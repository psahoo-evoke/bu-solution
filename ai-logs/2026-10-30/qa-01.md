## Prompt (summary or verbatim)
"ok proceed with scalability"

## Inputs used
- Discovery Q-002 (800 students × 10 courses a year), ADR 0007 (capacity), seed data in `data/synthetic/seed/`
- `backend/app/main.py` (status, review queue, export routes), `app/store.py`, `app/matcher.py`

## Output
- `backend/eval/run_volume.py`: adds N synthetic students (10 lines each; 65 % catalogue courses, 35 % new courses) to the in-memory store and times the real API routes through TestClient; PDF reading timed on the sample transcripts; repeatable (fixed seed), offline
- `docs/quality/scalability-report.md`: results at 0.1x, 0.5x, 1x, 2x and 5x, findings, 10x table, caveats
- README results section and `docs/roadmap.md` link the report; roadmap phase 3 gets "index transcript lines by student"
- Findings:
  - At 1x (804 students, 8,056 lines): status page p50 188 ms / p95 598 ms, queue refresh 0.5 s, export 0.24 s, peak memory 141 MB
  - Queue refresh and MyBU export grow quadratically: `Store.lines_for()` scans every line for each student
  - The first queue load after a restart ranks every waiting course in turn; the offline cache holds 4,096 courses
  - `app/matcher.py` defines `_RANK_CACHE` twice (lines 91 and 246); the second rebinds the first, so the offline and Azure engines share one dict with two different size limits. No failure today; reported, not changed.

## Human review
- No application code changed; the findings are for the developer role.
